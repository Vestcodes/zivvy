# Webhooks

> Webhooks are **live** — subscribe today from [Settings → Developer](https://zivvy.xyz/settings/developer) or via [`POST /v1/webhooks`](/docs#tag/Webhooks). 100+ event types across every resource, at-least-once delivery, HMAC-SHA256 signed.

Webhooks let your application receive real-time HTTP notifications when events happen in your Zivvy account — an order is submitted, an invoice is paid, stock levels change. Instead of polling the API, your server gets a POST request the moment something happens.

## How webhooks work

1. You register a webhook endpoint URL in the Zivvy dashboard.
2. You subscribe to one or more of the 100+ event types below (or use `*` to receive everything, or `sales-orders.*` to receive every event for a resource).
3. When a matching event occurs, Zivvy sends an HTTP POST request to your endpoint with a JSON payload describing the event.
4. Your endpoint responds with a `200` status to acknowledge receipt.

## Registering a webhook

In the dashboard, go to **Settings → Webhooks** and click **Create Webhook**:

- **URL** — The HTTPS endpoint on your server that will receive events. Must be publicly accessible and use HTTPS.
- **Events** — Select one or more event types to subscribe to, or choose "All events".
- **Secret** — A signing secret is generated automatically. Use it to verify that incoming requests are genuinely from Zivvy.

## Event types

Event names use the form `resource.action`, where the resource matches the plural slug in the REST API (e.g. `sales-orders`, `payment-entries`) and the action is one of the lifecycle stages below. Subscribe to individual events (`sales-orders.submitted`), a full resource (`sales-orders.*`), or every event (`*`).

## Payload format

Every webhook delivery is an HTTP POST with a JSON body. The following headers are always set:

| Header | Description |
|--------|-------------|
| `X-Zivvy-Event` | The event type, e.g. `sales-orders.submitted` |
| `X-Zivvy-Delivery` | A unique 32-character ID for this delivery attempt (use for deduplication) |
| `X-Zivvy-Signature` | `sha256=<hex>` — HMAC-SHA256 of the raw body, keyed by your webhook secret |
| `Content-Type` | Always `application/json` |

```json
{
  "event": "sales-orders.submitted",
  "resource": "sales-orders",
  "data": {
    "name": "SO-00042",
    "doctype": "Sales Order",
    "modified": "2026-07-25 14:30:00.123456",
    "customer": "Acme Corp",
    "status": "To Deliver and Bill",
    "grand_total": "12500.0"
  },
  "timestamp": "2026-07-25T14:30:00.123456"
}
```

| Field | Type | Description |
|-------|------|-------------|
| `event` | string | Event type in the form `resource.action` (e.g. `sales-orders.submitted`) |
| `resource` | string | Resource slug — matches the plural resource used in the REST API |
| `data` | object | Snapshot of the affected document at emit time |
| `data.name` | string | Unique document identifier (use with the REST API to fetch the full record) |
| `data.doctype` | string | Underlying doctype name (e.g. `Sales Order`) |
| `data.modified` | string | Last-modified timestamp of the document |
| `timestamp` | string | ISO 8601 timestamp of when the event was emitted |

The `data` object always contains `name`, `doctype`, and `modified`. Common fields (`customer`, `supplier`, `status`, `grand_total`, `employee`) are also included when present on the document. For the full record, use `data.name` with the corresponding REST endpoint — e.g. `GET /v1/sales-orders/{name}`.

## Signature verification

Every webhook request includes a signature in the `X-Zivvy-Signature` header. Verify this signature to ensure the request came from Zivvy and was not tampered with.

The signature is an HMAC-SHA256 hash of the raw request body, using your webhook secret as the key:

### Python

```python
import hmac
import hashlib

def verify_webhook(payload_body, signature_header, secret):
    expected = hmac.new(
        secret.encode("utf-8"),
        payload_body,
        hashlib.sha256
    ).hexdigest()

    return hmac.compare_digest(
        f"sha256={expected}",
        signature_header
    )
```

### JavaScript (Node.js)

```javascript
const crypto = require("crypto");

function verifyWebhook(payloadBody, signatureHeader, secret) {
  const expected = crypto
    .createHmac("sha256", secret)
    .update(payloadBody)
    .digest("hex");

  return signatureHeader === `sha256=${expected}`;
}
```

### Express middleware example

```javascript
app.post("/webhooks/zivvy", express.raw({ type: "application/json" }), (req, res) => {
  const signature = req.headers["x-zivvy-signature"];
  const secret = process.env.ZIVVY_WEBHOOK_SECRET;

  if (!verifyWebhook(req.body, signature, secret)) {
    return res.status(401).send("Invalid signature");
  }

  const event = JSON.parse(req.body);

  switch (event.event) {
    case "sales-orders.submitted":
      handleNewOrder(event.data);
      break;
    case "sales-invoices.paid":
      handleInvoicePaid(event.data);
      break;
    default:
      console.log(`Unhandled event type: ${event.event}`);
  }

  res.status(200).send("OK");
});
```

> Always verify the signature before processing a webhook. Never trust the payload without verification.

## Retry policy

If your endpoint does not respond with a `2xx` status within 10 seconds, Zivvy retries the delivery with exponential backoff:

| Attempt | Delay after previous attempt |
|---------|------------------------------|
| 1st retry | 1 minute |
| 2nd retry | 5 minutes |
| 3rd retry | 30 minutes |
| 4th retry | 2 hours |
| 5th retry | 12 hours |

After 5 failed retries, the delivery is marked as failed. You can view and manually retry failed deliveries in the dashboard under **Settings → Webhooks → Delivery Log**.

If your endpoint fails consistently for 3 consecutive days, the webhook is automatically disabled and you will receive an email notification.

## Handling webhooks correctly

- **Respond quickly.** Return a `200` status as soon as you receive the request. Process the event asynchronously (e.g., add it to a queue) rather than doing heavy work inline.
- **Handle duplicates.** Use the `X-Zivvy-Delivery` header to deduplicate. In rare cases (network issues, retries), you may receive the same delivery more than once.
- **Verify signatures.** Always check `X-Zivvy-Signature` before processing.
- **Use HTTPS.** Webhook endpoints must use HTTPS. Plain HTTP endpoints will be rejected.
- **Handle unknown events gracefully.** New event types may be added in the future. Your handler should not break if it receives an event type it does not recognize.

## Testing webhooks

During development, you can use tools like [ngrok](https://ngrok.com) or [localtunnel](https://localtunnel.github.io/localtunnel/) to expose your local server to the internet and test webhook deliveries.

The dashboard also includes a **Send Test Event** button for each webhook, which delivers a sample payload to your endpoint so you can verify your setup without waiting for a real event.
